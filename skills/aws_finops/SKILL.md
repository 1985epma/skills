## 🛠️ Technical Skill Specifications (JSON Schemas & SQL Logic)

### 1. `check_extended_support_charges`
* **Objective:** Identify if the newly closed or current invoice contains automated Extended Support fees for obsolete engines (e.g., RDS MySQL 5.7, PostgreSQL 11, or legacy EKS control plane versions).
* **Execution Window:** Days 01 to 05 (Immediate post-billing cycle close) and weekly tracking.

#### 🔹 Tool Definition Schema (JSON for AI Model)
```json
{
  "name": "check_extended_support_charges",
  "description": "Scans the AWS CUR for specific Extended Support billing line items generated by obsolete database engines or deprecated Kubernetes clusters.",
  "parameters": {
    "type": "object",
    "properties": {
      "linked_account_id": {
        "type": "string",
        "description": "Optional AWS linked account ID to scope down the search. If empty, searches globally across the Consolidated Invoice."
      },
      "billing_period": {
        "type": "string",
        "description": "Target billing month formatted as YYYY-MM (e.g., '2026-08')."
      }
    },
    "required": ["billing_period"]
  }
}
```

#### 💻 Reference SQL Query (Executed inside AWS Athena)
```sql
SELECT 
    line_item_linked_account_id AS account_id,
    line_item_product_code AS aws_service,
    line_item_usage_type AS usage_type,
    line_item_line_item_description AS description,
    ROUND(SUM(line_item_unblended_cost), 2) AS total_extended_support_cost,
    SUM(line_item_usage_amount) AS total_hours_charged
FROM 
    "athena_cur_database"."aws_cur_table"
WHERE 
    bill_billing_period_start_date = CAST('\${billing_period}-01' AS DATE)
    AND (
        LOWER(line_item_line_item_description) LIKE '%extendedsupport%'
        OR LOWER(line_item_line_item_description) LIKE '%extended support%'
        OR line_item_usage_type LIKE '%v1_2%' -- Catches legacy EKS control plane versions
    )
GROUP BY 
    1, 2, 3, 4
HAVING 
    SUM(line_item_unblended_cost) > 0
ORDER BY 
    total_extended_support_cost DESC;
```

### 2. `analyze_cost_anomaly_detail`
* **Objective:** Isolate specific cost variations between the current billing period and the previous month. It breaks down data to the most granular level (`UsageType` and `Operation`) to remove technical ambiguity for engineering squads.
* **Execution Window:** Active daily from day 01 until the last day of the month.

#### 🔹 Tool Definition Schema (JSON for AI Model)
```json
{
  "name": "analyze_cost_anomaly_detail",
  "description": "Compares specific AWS product costs between the current month and the previous month, itemizing by UsageType and Operation to isolate the root cause.",
  "parameters": {
    "type": "object",
    "properties": {
      "aws_service": {
        "type": "string",
        "description": "The exact AWS product code matching the CUR syntax (e.g., 'AmazonS3', 'AmazonEC2', 'AmazonRDS')."
      },
      "current_billing_period": {
        "type": "string",
        "description": "Current target month for analysis formatted as YYYY-MM."
      },
      "previous_billing_period": {
        "type": "string",
        "description": "Baseline historical month for delta comparison formatted as YYYY-MM."
      }
    },
    "required": ["aws_service", "current_billing_period", "previous_billing_period"]
  }
}
```

#### 💻 Reference SQL Query (Executed inside AWS Athena)
```sql
WITH current_month AS (
    SELECT 
        line_item_linked_account_id AS account_id,
        line_item_usage_type AS usage_type,
        line_item_operation AS operation,
        SUM(line_item_unblended_cost) AS cost_current
    FROM "athena_cur_database"."aws_cur_table"
    WHERE bill_billing_period_start_date = CAST('\${current_billing_period}-01' AS DATE)
      AND line_item_product_code = '\${aws_service}'
    GROUP BY 1, 2, 3
),
previous_month AS (
    SELECT 
        line_item_linked_account_id AS account_id,
        line_item_usage_type AS usage_type,
        line_item_operation AS operation,
        SUM(line_item_unblended_cost) AS cost_previous
    FROM "athena_cur_database"."aws_cur_table"
    WHERE bill_billing_period_start_date = CAST('\${previous_billing_period}-01' AS DATE)
      AND line_item_product_code = '\${aws_service}'
    GROUP BY 1, 2, 3
)
SELECT 
    COALESCE(c.account_id, p.account_id) AS account_id,
    COALESCE(c.usage_type, p.usage_type) AS usage_type,
    COALESCE(c.operation, p.operation) AS operation,
    ROUND(COALESCE(p.cost_previous, 0), 2) AS cost_prev_month,
    ROUND(COALESCE(c.cost_current, 0), 2) AS cost_curr_month,
    ROUND(COALESCE(c.cost_current, 0) - COALESCE(p.cost_previous, 0), 2) AS variance
FROM current_month c
FULL OUTER JOIN previous_month p 
    ON c.account_id = p.account_id 
    AND c.usage_type = p.usage_type 
    AND c.operation = p.operation
WHERE ABS(COALESCE(c.cost_current, 0) - COALESCE(p.cost_previous, 0)) > 10.00 -- Disregard noise below \$10.00 variance
ORDER BY variance DESC;
```

### 3. `calculate_financial_impact_runrate`
* **Objective:** Compute the moving daily burn rate over a recent window to generate a month-end landing projection (Forecast). Essential for flagging newly deployed rogue infrastructure before it completes a full billing cycle.
* **Execution Window:** Main focus during the second half of the month (Days 15-31).

#### 🔹 Tool Definition Schema (JSON for AI Model)
```json
{
  "name": "calculate_financial_impact_runrate",
  "description": "Calculates the recent daily spend average for a resource or account and projects its financial landing total for the last day of the current calendar month.",
  "parameters": {
    "type": "object",
    "properties": {
      "linked_account_id": {
        "type": "string",
        "description": "The specific AWS account ID experiencing the cost spike."
      },
      "days_to_analyze": {
        "type": "integer",
        "description": "Lookback window in days to establish the current trend average (Default: 7)."
      }
    },
    "required": ["linked_account_id"]
  }
}
```

#### 💻 Logic & Algorítmic Step (Processed via AI Python Environment)
1. The agent pulls the daily spend progression through Athena or the Cost Explorer API:
```sql
SELECT 
    line_item_usage_start_date AS usage_date,
    SUM(line_item_unblended_cost) AS daily_cost
FROM "athena_cur_database"."aws_cur_table"
WHERE line_item_linked_account_id = '\${linked_account_id}'
  AND line_item_usage_start_date >= CURRENT_DATE - INTERVAL '\${days_to_analyze}' DAY
GROUP BY 1
ORDER BY 1 DESC;
```
2. **Mathematical Execution (Done by Agent's internal code):**
   * `Month_To_Date_Cost`: Aggregated unblended cost from day 01 to the current date.
   * `Recent_Daily_Average`: Statistical average from the lookback output array above.
   * `Remaining_Days`: Calendar days remaining in the current month.
   * **`Month_End_Forecast`** = `Month_To_Date_Cost` + (`Recent_Daily_Average` * `Remaining_Days`)

## 🧠 Model Orchestration Instructions

When a user prompts the agent with an open-ended request like *"Audit our current billing variations"*, the agent must strictly execute the skills using this sequential loop:

1. **Trigger:** User uploads or references an anomaly or requests a month-end overview.
2. **Step 1 (Isolate EOL Debt):** Invoke `check_extended_support_charges` to filter out baseline technical debt penalties from standard cloud consumption.
3. **Step 2 (Deep Dive Granularity):** Execute `analyze_cost_anomaly_detail` on the high-variance services to map exact granular tags like `NatGateway-Hours` or `DataTransfer-Out-Bytes`.
4. **Step 3 (Financial Impact Assessment):** Trigger `calculate_financial_impact_runrate` to output a hard financial run-rate impact statement in USD, illustrating exactly what will happen if left unchecked until month-end closing.
